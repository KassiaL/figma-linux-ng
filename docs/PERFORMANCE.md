# Производительность и память

Все замеры: 23.10.2026, Ubuntu 24.04 X11, RTX 4060 (драйвер 580), 32 ГБ RAM, мониторы 60/60/75 Гц.
Файл — публичный пример из документации Figma (`nrPSsILSYjesyc5UHjYYa4`). Вход в аккаунт не
выполнялся, поэтому вкладки открывались в браузерном режиме (`--diag-no-desktop-bridge`).
Для сравнения собран **оригинальный** upstream Figma Linux (Electron 30.0.8) с вашими флагами из
snap (`enable-gpu-rasterization`, `enable-experimental-canvas-features`, `use-vulkan`,
`enable-features=Vulkan`). Он запускался на изолированном `HOME` и ваших данных не касался.

Важно: основную память занимает сам веб-редактор Figma. Renderer одного открытого файла —
0,5–0,7 ГБ, GPU-процесс — 0,2–0,45 ГБ. Это нельзя заметно уменьшить со стороны оболочки, и
форк этого не обещает.

## Сравнение с upstream (одинаковый сценарий)

| | upstream (Electron 30) | Figma Linux NG |
|---|---|---|
| WebGPU-адаптер во вкладке | `null` | NVIDIA Lovelace, аппаратный |
| Холст редактора готов, с момента запуска | 9,6 / 8,7 с | 6,9 / 6,0 с |
| Процессов с 1 файлом | 16 | 11 |
| PSS с 1 файлом | 1348 / 1263 МБ | 982 / 1096 МБ |
| PSS с 3 вкладками | 1857 / 1850 МБ | 2147 / 2070 МБ * |
| Фоновые вкладки: rAF за 2 с | 0 | 0 |

\* В upstream открытые из ссылки вкладки остаются в фоне и не рисуются, пока на них не
кликнуть. В NG новая вкладка сразу становится активной и отрисовывается. Поэтому сценарий
«3 вкладки» не полностью равноценный.

Откуда разница в процессах: upstream при старте каждого окна сразу загружает страницу
настроек, а в ней 4 `<webview>` превью тем. Это 4 лишних скрытых renderer'а со страницей Figma.
NG загружает настройки только при открытии окна настроек.

## Нагрузка CPU: две найденные причины

### 1. Вечный спиннер вкладки

Индикатор загрузки на вкладке гас **только** по сообщению Figma `setLoading(false)`. Если оно
не приходило (прототипы, сбои загрузки, ленивые вкладки), CSS-анимация крутилась бесконечно,
и окно перерисовывалось с частотой монитора. Теперь индикатор следует и за фактическим
состоянием загрузки страницы, а незагруженные (ленивые) вкладки не крутят его вовсе.

### 2. Вывод кадров через Vulkan-swapchain на X11/NVIDIA

Для WebGPU на X11 нужен `--enable-features=Vulkan`, и вместе с ним Chromium переводит на Vulkan
и композитор. Вывод через Vulkan-swapchain драйвера NVIDIA стоил GPU-процессу целое ядро при
любой непрерывной перерисовке. У upstream с вашими snap-флагами то же самое.

Анимация спиннера, CPU GPU-процесса:

| Профиль | GPU-процесс |
|---|---|
| OpenGL (Chromium по умолчанию, WebGPU недоступен) | 4,9 % |
| Vulkan (swapchain) | 101 % |
| ANGLE/Vulkan | 101 % |
| **Vulkan + `--disable-vulkan-surface` (по умолчанию в NG)** | **3,1 %** |
| то же + `__GL_YIELD=USLEEP` для swapchain | без изменений (101 %) |

Непрерывное панорамирование холста, окно 1600×900 на мониторе 75 Гц:

| Профиль | FPS | CPU всего |
|---|---|---|
| OpenGL | 62,5 | 131 % |
| Vulkan swapchain | 89,8 | 130 % |
| **Vulkan + blit (NG по умолчанию)** | 60 / 60 | **87 % / 85 %** |
| upstream, его флаги (окно 1200×860) | 85,5 | 158 % (из них GPU-процесс 101 %) |
| NG по умолчанию (окно 1200×860) | — | 46 % (GPU-процесс 20 %) |

Компромисс профиля по умолчанию: на мониторе выше 60 Гц вывод ограничен ~60 к/с. Если частота
важнее CPU, выберите в настройках профиль `vulkan-swapchain`.

Простой с открытым файлом после исправлений: всё приложение 1–2 % CPU, GPU-процесс 0,2–1 %.

## Что ещё изменено в оболочке

- **Ленивое восстановление вкладок.** После перезапуска загружается только активная вкладка,
  остальные — при первом клике. Замер: 3 восстановленные вкладки — 442 МБ на всё приложение,
  после клика по одной — 1225 МБ (+680 МБ за один файл).
- **Утечки.** `closeAllTab()` (выход, нет сессии) раньше только очищал список, а renderer'ы
  вкладок продолжали жить. Закрытое окно не уничтожало webContents своих вкладок. Каждое окно
  навсегда добавляло глобальные обработчики `app.on`/`ipcMain.on`. Наблюдатели файлов
  локальных плагинов не снимались при закрытии вкладки. Проверено: после закрытия второго окна
  его webContents уничтожены, число глобальных обработчиков вернулось к значению для одного окна.
- **Шрифты.** `getFonts`/`getModifiedFonts` каждый раз запускали синхронный `find` в main-процессе
  (подвисали все окна) и заново читали и разбирали все файлы шрифтов (здесь 2617 файлов). Теперь
  обход асинхронный, разобранные шрифты кэшируются по mtime/size, параллельные запросы
  объединяются. Повторный запрос из кэша — 34 мс.
- **Логи.** Один поток записи вместо открытия файла на каждую строку. Убран `console.log`
  каждого сообщения моста (при открытых DevTools он удерживал в памяти большие буферы).
- **Кэш.** HTTP-кэш лежит в `~/.cache/figma-linux-ng` и **не** очищается при запуске:
  повторное открытие файлов Figma идёт из кэша.

## Как повторить замеры

```bash
python3 scripts/diag/cpu-report.py "/opt/Figma Linux NG/figma-linux-ng" 10
```

```bash
python3 scripts/diag/proc-report.py $(pgrep -o -f "/opt/Figma Linux NG/figma-linux-ng")
```

Для старого клиента подставьте `/snap/figma-linux/197/figma-linux`.
